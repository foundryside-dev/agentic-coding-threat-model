## Rule description

Catching all exceptions broadly prevents crashes but also prevents errors from being recorded. In high-assurance contexts, unrecorded errors are worse than crashes.

## Specification

**Severity matrix row:**

| Audit Trail | Pipeline | Shape Val. | Ext. Raw | Unk. Raw | Unk. Shape V. | Unk. Sem. V. | Mixed Raw |
|---|---|---|---|---|---|---|---|
| E/U | E/St | W/St | W/R | E/St | W/St | W/St | E/St |

WL-003 has the most variation across the matrix of any rule. It is the only rule that uses all four severity/exceptionability combinations (E/U, E/St, W/St, W/R).

## Rationale

The severity variation across contexts reflects the different risk profiles of broad exception catching:

- **AUDIT_TRAIL (E/U):** In authoritative contexts, broad exception handling is unconditionally wrong. It prevents integrity failures from being detected.
- **PIPELINE (E/St):** Pipeline contexts feed downstream consumers; broad catches degrade diagnostic fidelity for transformation errors. ERROR but governable.
- **SHAPE_VALIDATED (W/St):** Shape-validated data has known structure, so broad exception catching is more suspicious — structural uncertainty has been resolved, and the remaining exceptions are more likely to signal semantic or logic errors that should surface. But the data's values are still unchecked, and semantic-validation logic may legitimately use broad catches as a defensive measure while checking domain constraints. Hence WARNING rather than ERROR — suspicious, not categorically wrong.
- **EXTERNAL_RAW (W/R):** Broad exception catching during parsing is tolerable (external data is expected to be malformed), so RELAXED governance suffices.
- **UNKNOWN_RAW (E/St):** More severe than EXTERNAL_RAW. In unknown-origin data, the same pattern masks dangerous uncertainty: the code does not know whether the data is malformed external input or corrupted internal state, and the broad catch prevents the distinction from surfacing.
- **MIXED_RAW (E/St):** Mixed-provenance data carries the same uncertainty as unknown-origin data.

## Examples

**Agent-generated (violation in Tier 1 context):**
```python
@tier1_read
def load_audit_record(record_id: str) -> dict:
    try:
        record = db.fetch(record_id)
        return record
    except Exception:  # WL-003: broad catch in audit context
        return {"status": "error"}
```

**Correct:**
```python
@tier1_read
def load_audit_record(record_id: str) -> dict:
    record = db.fetch(record_id)  # Let exceptions propagate — integrity failure
    return record
```

## Detection approach

Static analysis tools detect broad exception handler patterns — `except Exception:`, `except BaseException:`, bare `except:` in Python; `catch (Exception e)`, `catch (Throwable t)` in Java — and check the taint state of the enclosing function against the severity matrix.

## Related rules

WL-003 frequently fires alongside [WL-001]({{< relref "wl-001" >}}) (fallback defaults) and [WL-005]({{< relref "wl-005" >}}) (audit writes in broad handlers). The combination of broad exception handling with fallback defaults is the canonical pattern of agent-generated "defensive" code applied to authoritative data.

WL-003 is distinct from [WL-004]({{< relref "wl-004" >}}) (silent exception catching): WL-003 catches the *breadth* of the exception handler; WL-004 catches the *emptiness* of the handler body.
